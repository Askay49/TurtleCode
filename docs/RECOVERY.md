# Сохранность документов и восстановление

Реализовано 4 ноября 2026 года. Код: `document/RecoveryStore`,
`document/FileState`, интеграция в `MainWindow` и `EditorWidget`.

## Закрытие и сохранение

Закрытие вкладки, всех вкладок, окна и команда Quit используют Save / Discard /
Cancel. Все вкладки закрываемого набора остаются открытыми до завершения
подтверждений и успешных сохранений. Отмена не отменяет уже выполненное
сохранение другого документа, но сохраняет весь набор вкладок открытым.

Занятый документ, незавершённый rename/project replace блокируют закрытие:
пользователь получает сообщение о необходимости дождаться операции.
Сохранение при выходе асинхронное; ошибка или отмена сохранения отменяет выход.
Во время согласования нельзя открыть новые документы в закрываемом окне;
редакторы и основные команды временно недоступны.

При сохранении сравниваются dev/inode, размер и mtime/ctime с наносекундами.
Внешнее изменение или удаление вызывает выбор Overwrite / Save As / Cancel.
Повторная проверка выполняется в worker перед записью и непосредственно перед
атомарным commit QSaveFile. Это обнаружение конфликтов, а не файловая блокировка:
остаётся узкое окно гонки с внешним писателем между последней проверкой и rename.
Save As использует подтверждение замены выбранного файла файловым диалогом.

## Автоматическая копия

В «Настройки → Редактор» есть переключатель «Автоматически создавать резервные
копии несохранённых документов» (`editor/recoveryEnabled`, по умолчанию true).
Save применяет его без перезапуска, Cancel не меняет настройку. При отключении
новые snapshots и payload резервных копий не создаются; уже начатая запись может
завершиться. Существующие копии сохраняются и остаются доступны для восстановления.
Состояние workspace/вкладок/курсоров по-прежнему запоминается. После повторного
включения текущие несохранённые изменения автоматически попадут в новую копию.

Изменённые документы резервируются через 2 секунды после остановки ввода,
с дополнительным таймером 15 секунд при продолжающихся правках. Периодический
проход каждые 10 секунд также сохраняет состояние workspace и навигации.
Эти интервалы — расписание попыток, а не гарантированная граница потери данных:
занятые документы, текущая запись, медленный диск и ошибки могут увеличить отставание.

Хранилище: `QStandardPaths::AppDataLocation/recovery/<window UUID>/`.
На типичной Linux-системе это `~/.local/share/Turtle Code/Turtle Code/recovery/`.
Каждое окно держит QLockFile; активное хранилище другого процесса пропускается.
Каталог создаётся с правами только владельца.

Для документа существуют:

- `<id>.data` — добавляемые неизменяемые фрагменты текста;
- `<id>.json` — атомарно заменяемый список диапазонов, контрольные суммы и метаданные;
- `session.json` — workspace, документы, текущий документ, курсоры и прокрутка.

Первая запись помещает весь текущий текст в `.data`. Следующие записи используют
стабильные идентификаторы исходных хранилищ piece tree и добавляют только ещё
не записанные фрагменты. Изменение разрезанного фрагмента может повторно записать
его части, обычно до нескольких КиБ. Это журнал фрагментов, а не журнал команд
Undo. Смена/компактизация исходного хранилища может потребовать большей записи.

На UI-потоке фиксируется согласованный snapshot: клонируются узлы дерева и
resident-арены, дисковые backing files разделяются. Дисковые чтения, добавление
данных, хеширование и подготовка manifest выполняются worker-ом. На окно
допускается один recovery worker; накопления очереди snapshot-ов нет.

Перед публикацией manifest данные сбрасываются через fsync; manifest записывается
через QSaveFile с fsync, затем синхронизируется каталог. Недописанный хвост `.data`
не используется, поскольку предыдущий manifest на него не ссылается.
Manifest ограничен 128 МиБ; превышение вызывает ошибку резервирования, сохраняя
предыдущую точку восстановления.

Ошибка показывает постоянное сообщение «Копия восстановления устарела» с причиной
в подсказке. Текст остаётся доступным; последующие попытки продолжаются.
Успешная запись убирает предупреждение. После успешного сохранения исходника и
публикации актуального сеанса ненужная копия удаляется. При явном Discard она
также удаляется, в том числе из хранилища, откуда документ был восстановлен.

## Следующий запуск

Обычный запуск восстанавливает последний корректно закрытый сеанс: workspace,
файлы, активный документ, курсоры и прокрутку. При явных CLI-путях чистый сеанс
не подмешивается. `--new-window` не импортирует предыдущие сеансы автоматически.

Несохранённые документы предыдущих завершившихся процессов вызывают предложение
«Восстановить / Позже». «Позже» сохраняет данные для следующего запуска.
Восстановленные документы помечаются modified; исходные файлы не записываются.
Сохраняется исходная файловая сигнатура, поэтому внешнее изменение за время
простоя обнаруживается при последующем Save. Если путь уже открыт другим буфером,
восстановленный буфер отсоединяется от пути и сохраняется через Save As.

Восстановление проверяет границы диапазонов, длину текста и SHA-256 фрагментов.
Повреждённая копия вызывает ошибку и сохраняется для расследования. Уже открытый
буфер не подменяется частичным результатом. Если первый document manifest успел
записаться до аварии, а session manifest ещё нет, такой документ тоже обнаруживается.
Исходные recovery-каталоги удерживаются заблокированными до переноса в новое
хранилище; при ошибках исходные данные сохраняются.

## Ограничения первой реализации

- Временное runtime-хранилище ChunkedFile остаётся отдельным. Первая recovery-копия
  требует дополнительной полной записи на постоянный диск; общего backing store
  между runtime и восстановлением пока нет.
- Snapshot и manifest требуют O(числа фрагментов) времени и памяти; метаданные
  snapshot фиксируются на UI-потоке. Это не гарантия отсутствия пауз на гигабайтных
  или сильно фрагментированных документах. Такое профилирование ещё требуется.
- Журнал не компактизируется автоматически и не имеет общей дисковой квоты.
  Закрытие/отбрасывание и успешное сохранение освобождают ненужные данные.
- История Undo, выделения и несколько курсоров после перезапуска не восстанавливаются.
- Восстановление большого документа требует временной сборки его текста на диске,
  затем обычной загрузки буфера. Во время этой операции документ занят.
- Восстанавливается последняя успешно опубликованная копия. fsync не защищает
  от неисправности накопителя/файловой системы; реальное отключение питания
  в этой проверке не моделировалось.

## Проверки

`recovery`: disk-backed файл 8 МиБ, малые правки без полной повторной записи,
повторный checkpoint без роста payload, spill вставок, BOM/CRLF/Unicode,
принудительное завершение дочернего процесса с недописанным хвостом и активным
lock, повреждение payload, checkpoint без session manifest, удаление копий.

`document-safety`: отмена закрытия/Quit, сохранение перед выходом, отказ принять
новые пути во время выхода, внешнее изменение/Overwrite/Cancel, ошибка сохранения,
автоматическое резервирование с ошибкой диска и повторной попыткой, восстановление
modified-буфера и чистого сеанса с навигацией.

Измеренный пример: малая правка в 8-МиБ документе добавила 4103 байта payload;
checkpoint без новой правки не увеличил `.data`. Это не замер задержки ввода
и не проверка гигабайтных файлов. Qt 6.2.4 и реальная desktop/IME-сессия отдельно
не запускались.
